# ADR-001: C++20 + JUCE + causal DSP + symbolic generation

日付: 2026-11-03 / 状態: プロトタイプに採用。スタジオ受け入れは未完了。

## 背景

生ドラムが主導するセッションでは、平均推論速度より発音時刻の安定性が重要。Windows 11 / UR22C、オフライン、DAW不要。入力の拍が曖昧な場合に、モデルが自信を持って誤った拍を生成する構成は避けたい。

## 決定

C++20の独立エンジン、JUCE 9.0.5のASIO/WASAPI・GUI・MIDI・WAV I/Oを採用。音源は同梱の加算合成ベース。外部モデル・SoundFontは不要。拍追従は5 msの特徴フレーム、重み付きオンセット間隔の周期評価、位相修正、倍半テンポのヒステリシスで実装する。

音声コールバックから固定容量SPSCキューで特徴を解析ワーカーへ送り、時刻付きStateと先読みPhraseを返す。発音は音声サンプルクロックで決める。GUI、ファイル読込、MIDIドライバー呼出し、生成はコールバック外。

生成はマイナースケール・共有コードルート・モチーフ・確率的装飾・繰り返し。学習済み生成AIではない。MIDIループファイルの再生でもない。現在はベースだけ。今後の重いモデルは解析とは別のワーカーへ置き、同じPhrase契約に変換する。

## 他案

- Rust + CPAL + egui: メモリ安全性と許諾ライセンスが魅力。ただしASIO・入出力同期・デバイスGUI・MIDI・音源の結合作業が多い。本案件では安全性だけでなく音声機器統合の検証コストを重視。
- C++ + PortAudio + Qt: 音声I/Oは適切。GUI/デバイス管理/音源の接続量とQt配布が増える。JUCEから乗り換える性能根拠は未取得。
- Python/PortAudioやC#/NAudioを音声コールバックの中心にはしない。GC・ランタイム・FFIの停止要因を避ける。Pythonは将来のモデル実験に限定可能。

## 不利益と変更条件

JUCEのAGPLv3または商用ライセンスが配布方針に影響する。本プロトタイプはAGPLv3で構成し、公開・配布は実施しない。非公開ソースでの製品配布を決める際はJUCE商用条件とASIO条件を確認する。

自作トラッカーは実録音の一般化が未知。合成音源に合うことを生ドラム対応完了と扱わない。実録音コーパスでaubio/ML方式が明確に勝つ場合、Trackerを交換する。音質が体験を損なう場合はSoundFontの権利を確認してFluidSynthを追加する。

実測の比較は現時点では採用案のコアとJUCEだけ。他候補を同一機材でベンチマークしたとは主張しない。選定根拠と公式情報は[技術比較](TECHNOLOGY.md)、測定条件は[検証](VALIDATION.md)に分離する。
